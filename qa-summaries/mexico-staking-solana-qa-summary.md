# Саммари чата — QA Mexico Staking через Claude Code

## Контекст и цель

Разговор начался с задачи: получить доступ к репозиторию проекта Mexico Staking (MEX, стейкинг на Solana, devnet, `dark-dao`) и протестировать его через Claude. Сначала — саммари четырёх лекций/обсуждений про Claude Code для QA (Tools, MCP, CLAUDE.md, Skills, Hooks, управление контекстом, human-in-the-loop, узкие батчи вместо одной большой задачи). Дальше — практическая работа: собран кастомный скилл и пройден полный путь от локальной настройки до реального тестирования смарт-контракта.

## Скилл `solana-staking-qa`

Собран, урезан до сути и передан пользователю как `.skill`-файл и как чистый `SKILL.md` (для ручной установки в `.claude/skills/solana-staking-qa/SKILL.md` внутри проекта). Ядро скилла:

- **Принцип**: на Solana фронт — только UX, программа — источник правды; любое ограничение проверять дважды — через UI и в обход UI (прямой запрос).
- **Три узких прохода**: smoke (happy path) → break it (обход валидации, IDOR, race conditions) → Solana-специфика.
- **Чек-лист Solana-специфики**: rent, ATA, compute budget при множестве позиций, подмена PDA, on-chain Clock vs. клиентское время, атомарность транзакций, порог мультисига, округление наград, утечка RPC-ключа в Network tab.
- **Отдельный раздел** про активный поиск уязвимостей и корнер-кейсов: граничные значения ровно на лимите, экстремумы, необычный порядок действий, прерванные транзакции, access control на каждой инструкции напрямую, арифметика на экстремумах.
- Формат вывода — без навязанного CSV, по контексту; human-in-the-loop как отдельное явное правило.

## Локальная установка toolchain — сага с WSL2

Самая долгая часть сессии. Родная (native Windows) сборка `cargo build-sbf`:

1. Сначала упала на отсутствии `link.exe` (MSVC toolchain без Build Tools, C: почти без места — 3.27 GB).
2. Переключились на GNU-toolchain (свой линкер, весь на D:) — линковка заработала.
3. Solana CLI 4.1.2 поставлен через прямой GitHub-релиз (официальный установщик был недоступен).
4. `cargo build-sbf` упал дважды подряд с одинаковой внутренней паникой (`toolchain.rs:357`, `Option::unwrap()` на `None`) — баг самого инструмента на Windows, воспроизводился и на MSVC, и на GNU toolchain.

Решение — переход на запасной план (WSL2 + Ubuntu), который обсуждался ещё на этапе выбора пути установки:

- Включён WSL2 через `dism.exe` (два компонента + перезагрузка).
- Ubuntu 22.04 установлена с явным `--location` на D:, чтобы не повторить историю с забитым C:.
- Rust + Solana CLI 4.1.2 подняты внутри WSL, проект скопирован в native ext4 (`/root/work/dark-dao`, не через `/mnt/c` — слишком медленно).
- `cargo build-sbf` в WSL прошёл чисто, `staking.so` собран (553800 байт).

Также по ходу: диагностирована и предотвращена вторая потенциальная проблема с диском — `cargo-build-sbf` по умолчанию качает platform-tools в `%USERPROFILE%\.cache\solana` на C:, а не в настроенные переменные окружения; решено через directory junction на D:.

## Тестирование — что сделано

**Базовый регресс.** Весь существующий `cargo test -p staking-test-harness`: **407 passed / 0 failed** на 33 целях (для сравнения — аудит от 18.08.2026 фиксировал 339/31, покрытие с тех пор выросло).

**`stake` — happy path (STK-01–03).** Подтверждены реальным прогоном (`epic_3_staking`), не просто чтением кода.

**Integration (сквозные сценарии, INT-01…04a).** Написан новый файл `integration_flows.rs`, 8 passed / 0 failed: полная цепочка stake→check_in→claim→compound→unstake, `settle` от постороннего не меняет чужую выплату, `update_config` не трогает уже открытые позиции, два стейка (в отдельных и в одной транзакции) не могут вместе превысить кошельковый кап. По ходу найдена и исправлена ошибка в самом тесте (не в программе) про сброс `progression`.

**Vulnerabilities — батч 1 (Access control, AC-01–03).** Все три — **enforced**. Закрыты реальные пробелы в тестовом покрытии (не в программе): админская инструкция с названным, но неподписавшим authority; IDOR-тест на `compound`, которого не было; edge case с вытесненной заявкой на смену authority.

**Vulnerabilities — батч 2 (`init_if_needed` reentrancy, RI-01–03).** Тоже **enforced** — переиспользование индекса закрытой позиции блокируется монотонностью `next_position_index`. Найден маленький баг в самом харнессе (не в проде): хелпер `next_position_index` ломается на предварительно профинансированном `User` PDA.

**Батч 3 (арифметика на экстремумах)** — поставлен в очередь, ещё не выполнен на момент саммари.

## Что осталось пустым/незакрытым

- 13 из 16 инструкций (`unstake`, `claim`, `compound`, `check_in`, `settle`, `initialize_pool`, `update_config`, `pause`, `resume`, `top_up_vault`, `withdraw_vault`, `set_restriction`, `clear_restriction`, `propose_authority`, `accept_authority`) — разделы плана пустые, ни одной строки.
- Договорились закрывать их **дёшево**: grep по существующим epic-тестам вместо новых прогонов через WSL — это покроет happy path почти бесплатно; corner-case/vulnerability для них — отдельно и позже, осознанно, не вслепую.
- Известные находки, требующие внимания:
  - **ISSUE-01** (🔍, не подтверждено): `init_if_needed` на `Stake.user` — впоследствии батч 2 подтвердил, что это **enforced**, не уязвимость.
  - **ISSUE-02** (🚫): утечка Helius/RPC-ключа во фронтенде — найдена в самом начале по скриншотам, фронтенд в этой сессии не открывался, статус не проверен.
  - **ISSUE-03** (🚫): подозрение на округление/потерю пыли на `claim` — инструкция `claim` вообще не тестировалась.
- **Фронтенд/UI-слой целиком не начат** — все три оригинальных CSV-чеклиста (smoke/break/Solana-специфика) были про реальный сайт (`mexicoweb-dev.up.railway.app`) и Phantom, но вся эта сессия ушла в бэкенд (`cargo test`).

## Рабочая дисциплина, которая закрепилась по ходу

- Один инструкция/тема за раз, план → ревью человеком → верификация реальным прогоном → сохранение в `test-plan.md` — и только потом следующий батч.
- `test-plan.md` **никогда не пересоздаётся** — только дополняется точечно, и только по явной команде сохранить (само по себе ничего не пишется).
- Модель/effort под тип задачи: Sonnet + Medium для механики (установка, прогон, сохранение), Opus + High + Thinking для анализа уязвимостей и корнер-кейсов.
- Экономия токенов: не гонять WSL-компиляцию там, где хватает grep по существующим тестам; короткий формат вывода вместо пересказа кода.

## Актуальный следующий шаг на момент саммари
