# Тест-план: `unstake` (Mexico Staking, dark-dao)

Статус: **draft, не верифицирован**. Составлен по методике скилла `solana-staking-qa`
(smoke → break it → Solana-специфика, плюс арифметика на экстремумах и интеграционные
пересечения). Перед прогоном — ревью человеком; после — верификация реальным `cargo test`
(happy path — дёшево через grep по существующим epic-тестам, corner-case/vulnerability —
новыми тестами в `staking-test-harness`).

## 1. Smoke / happy path

- **UNSTK-01** — Пользователь может анстейкнуть позицию после окончания лок-периода;
  средства (principal) возвращаются на корректный token account.
- **UNSTK-02** — После анстейка позиция закрывается/деактивируется, повторно
  использовать этот же индекс/аккаунт нельзя.
- **UNSTK-03** — Rent-exempt лампорты закрытого аккаунта позиции возвращаются
  правильному получателю (владельцу позиции, а не платящему за tx).
- **UNSTK-04** — Анстейк одной из нескольких открытых позиций пользователя не
  затрагивает остальные (баланс, статус, индексы).
- **UNSTK-05** — Баланс vault уменьшается ровно на сумму principal (+ pending reward,
  если `unstake` заодно рассчитывает и выплачивает награду).
- **UNSTK-06** — Состояние `User`/`Stake` PDA после анстейка корректно отражает
  "closed"/"unstaked" (счётчики открытых позиций, флаги и т.п.).

## 2. Break it — валидация, access control, IDOR

- **UNSTK-07** — Анстейк до конца лок-периода отклоняется (если программа
  ограничивает минимальный срок стейка).
- **UNSTK-08** — Анстейк может выполнить только владелец позиции/подписант `User`
  PDA; попытка от другого signer'а должна провалиться.
- **UNSTK-09** — IDOR: подстановка чужих аккаунтов позиции/`User` при подписи
  атакующим (напрямую, минуя UI) должна провалиться.
- **UNSTK-10** — Повторный анстейк уже закрытой позиции (double-unstake / replay)
  должен провалиться.
- **UNSTK-11** — Анстейк на паузе программы (`pause`) отклоняется, если пауза
  распространяется на пользовательские инструкции.
- **UNSTK-12** — Анстейк для пользователя с активным `set_restriction` отклоняется.
- **UNSTK-13** — Подмена destination-аккаунта (ATA, не принадлежащий владельцу
  позиции) — должна провалиться, средства не должны уйти на чужой аккаунт.
- **UNSTK-14** — Подмена vault-аккаунта — должна провалиться (проверка seeds/PDA).
- **UNSTK-15** — Отсутствующая/некорректная подпись на обязательных аккаунтах —
  инструкция должна провалиться.
- **UNSTK-16** — Позиция/аккаунты, принадлежащие другому pool/config, не должны
  проходить как валидные для анстейка в текущем пуле.
- **UNSTK-17** — Реентрантность: два вызова `unstake` для одной и той же позиции в
  одной транзакции (если возможно через CPI/повторную инструкцию) — не должно
  приводить к двойной выплате.

## 3. Solana-специфика

- **UNSTK-18** — Compute budget: достаточен ли лимит, если `unstake` в одной
  транзакции с `claim`/`compound` (расчёт награды + closure аккаунта).
- **UNSTK-19** — Проверка лок-периода идёт по on-chain `Clock`, а не по
  клиентскому/переданному timestamp — попытка передать "своё" время не должна
  влиять на результат.
- **UNSTK-20** — Rent: лампорты закрытого аккаунта уходят корректному получателю,
  а не тому, кто оплачивает транзакцию (если это разные аккаунты).
- **UNSTK-21** — ATA: авто-создание/использование associated token account для
  destination — корректный owner и mint.
- **UNSTK-22** — Атомарность: если анстейк+settle падает на середине (например,
  недостаточно средств в vault для выплаты награды), вся транзакция откатывается —
  позиция не закрывается без реального перевода средств.
- **UNSTK-23** — Проверка PDA seeds: аккаунт с "похожей" структурой, но неверными
  seeds не должен проходить как валидный (Anchor `seeds` constraint).
- **UNSTK-24** — Анстейк нескольких позиций в одной транзакции — нет порчи общего
  состояния (счётчики, суммарные лимиты) и нет двойного учёта.

## 4. Арифметика на экстремумах

- **UNSTK-25** — Анстейк максимально возможной суммы (близко к `u64::MAX` или к
  сконфигурированному капу) — без overflow в расчёте выплаты.
- **UNSTK-26** — Анстейк сразу после стейка минимально допустимой суммы —
  без underflow, без проблем с rent.
- **UNSTK-27** — Анстейк с pending reward = 0 (например, ровно на границе
  check-in интервала) — без деления на ноль и без отрицательной награды.
- **UNSTK-28** — Анстейк долго открытой позиции с максимально накопленной
  наградой (близко к переполнению аккумулятора) — проверить checked/saturating
  арифметику, а не wrapping.
- **UNSTK-29** — Consistency check: `vault_before - vault_after == principal +
  reward_paid` (с точностью до ожидаемого округления) — ни лишние токены не
  создаются, ни "пыль" не теряется незаметно.

## 5. Пересечения с другими инструкциями (интеграционные корнер-кейсы)

- **UNSTK-30** — `unstake` сразу после `compound` — компаундированный principal
  учитывается корректно при анстейке.
- **UNSTK-31** — `unstake` после `update_config`, изменившего лок-период/reward
  rate — явно проверить и задокументировать фактическое поведение для уже
  открытых позиций (аналогично INT-03, но для `unstake`).
- **UNSTK-32** — Конкурирующий `withdraw_vault` от админа в момент анстейка —
  vault не должен уйти в отрицательный баланс / инструкция должна упасть
  безопасно, а не запаниковать.
- **UNSTK-33** — Анстейк, когда `top_up_vault` не пополнялся и баланс vault меньше
  суммарной задолженности по выплатам — должен безопасно провалиться, а не
  выполнить частичную/неверную выплату.

## 6. Frontend (если/когда фронтенд войдёт в скоуп)

- Кнопка "Unstake" заблокирована/показывает countdown до конца лок-периода.
- Корректно отображаемая сумма к выплате (principal + reward) до подтверждения.
- Обработка ошибки on-chain вызова (например, отклонённая транзакция) — понятный
  тост/сообщение, без "зависшего" UI.
- Защита от двойного сабмита (двойной клик = одна транзакция, а не две).
- Wallet-flow (Phantom): подтверждение/отклонение анстейка обрабатываются корректно.
- Утечка RPC/Helius-ключа в Network tab при вызове анстейка (см. ISSUE-02) — не
  проверялось, статус открыт.
