# Саммари чата — QA Mexico Staking, сессия 2 (Cursor Cloud Agent)

Продолжение работы, описанной в `mexico-staking-solana-qa-summary.md`. Эта сессия велась в облачном агенте Cursor поверх репозитория `New_rep`, в котором **нет** реального кода `dark-dao`/Mexico Staking — репозиторий используется только как архив QA-заметок. Реальный код, `cargo test`, WSL2-окружение — всё это в отдельном локальном проекте пользователя, здесь не воспроизводилось.

## Что сделано в этой сессии

### 1. Черновики тест-планов (в `qa-summaries/`)

Собраны по методике скилла `solana-staking-qa`, в табличном формате, совпадающем со схемой реального `test-plan.md` проекта (`ID | Тип | Что проверяем | Ожидаемое поведение | Статус | Примечание`, легенда статусов ⬜/✅/❌/🔍/🚫, типы HP/BV/CC/SEC/SOL):

- **`test-plan-unstake.md`** — 24 кандидатных кейса. Осознанный перекос в сторону SEC/CC/BV, потому что happy path уже покрыт `epic_5_position_exit` (22/22 в регрессе). Наибольший приоритет — UNSTK-06 (IDOR на `position`, прямой аналог найденного пробела CMP-01), UNSTK-17/19/21 (гонки с `pause`/`withdraw_vault`/`set_restriction`, помечены 🔍 — сначала спека).
- **`test-plan-pool-invariants.md`** — сквозные (не привязанные к одной инструкции) кейсы на консервацию значения и платёжеспособность пула: `stake_vault` ⇄ `Σ(principal открытых позиций)`, `reward_vault` ⇄ `Σ(accrued)`, полный soak-тест на случайной последовательности всех 16 инструкций, отсутствие смешивания источников выплат между `stake_vault`/`reward_vault`.
- **`test-plan-claim.md`** — 18 кандидатных кейсов, акцент на точность/округление (открытый ISSUE-03 — `claim` вообще не тестировался) и стандартный SEC-чек-лист подмен аккаунтов.
- **`test-plan-check_in.md`** — 14 кандидатных кейсов, акцент на границы UTC-дня и правило "паузные дни не считаются пропущенными" (та же логика, что уже один раз дала ложный провал теста STK-04/INT-01a).
- **`test-plan-compound.md`** — дополнение к существующему в реальном проекте CMP-01: остальные пункты SEC-чек-листа + ключевой открытый вопрос (CMP-06), реально ли компаунд двигает токены между `reward_vault`/`stake_vault`, или это чисто внутренняя переоценка `accrual_base` без трансфера — от ответа зависит формулировка инвариантов пула для этой инструкции.

### 2. Закреплённая методология (повторяемый процесс на инструкцию)

1. Проверить по статусной таблице реального `test-plan.md`, покрыт ли happy path существующим epic-тестом — если да, не переписывать, только строка-привязка к ID.
2. Прочитать хендлер инструкции в `lib.rs` — какие constraints уже стоят (`has_one`, `Signer`, `seeds`, `token::authority`), какая арифметика.
3. Прогнать через стандартный чек-лист подмен, доказавший ценность на `stake` (STK-37…61) и на точечных SEC-пробах (`compound`/`pause`/`accept_authority`): подмена каждого аккаунта, IDOR, подписант назван но не подписал, делегат вместо владельца, не-каноничный bump, повторная отправка транзакции, переиспользование индекса, гонки с `pause`/`update_config`/`withdraw_vault`/`set_restriction` в одной транзакции.
4. Черновик → ревью человеком → прогон в WSL → перенос построчно в реальный `test-plan.md` (файл никогда не пересоздаётся).

Рекомендованный приоритет по оставшимся 13 инструкциям (по риску, не по алфавиту): `unstake` (деньги выходят + закрытие аккаунта) → `claim` (висит ISSUE-03) → админские с деньгами/доступом (`update_config`, `set_restriction`/`clear_restriction`, `withdraw_vault`/`top_up_vault`) → `settle`/`check_in`/`initialize_pool` → `resume` (дёшево, зеркало уже закрытого `pause`).

Везде, где поведение зависит от незафиксированного явно правила спеки (блокирует ли `pause`/`set_restriction` конкретную инструкцию, резервирует ли программа `reward_vault` под начисленные-но-не-выплаченные награды) — кейс помечается 🔍 с явной инструкцией сначала свериться с `PRD.md`/`DECISIONS.md`, а не угадывать ожидаемый результат.

### 3. Концептуальный разбор: зачем проверять баланс пула, если "токены никуда не деваются"

Ключевое разделение: на уровне SPL Token toкены действительно не исчезают (перевод только переносит баланс; наличие `top_up_vault`/`withdraw_vault` говорит, что награды не минтятся на лету, а идут из заранее заполненного `reward_vault`). Но это ничего не гарантирует про **внутренний учёт программы** (`Pool.total_staked_principal`, `User.staked_principal`, `accrued`/`accrual_base`) — он может разойтись с реальными балансами vault'ов из-за багов, и это не видно ни в одном отдельном happy-path тесте. Отсюда — набор инвариантов в `test-plan-pool-invariants.md`, включая обобщение существующего STK-06 (сейчас проверяется только `>=` и только после `stake`) на равенство после **любой** инструкции.

### 4. Наблюдения из ручного тестирования реального сайта (`mexicoweb-dev.up.railway.app`, Phantom, devnet)

Это первый раз в ходе всей QA-работы, когда фронтенд реально открывался (раньше — только `cargo test`), пользователь показывал скриншоты Phantom и Solana Explorer:

- **Compute Budget инструкции** (`set_compute_unit_price` + `set_compute_unit_limit`) идут внутри той же транзакции, что и основной вызов программы — не отдельная "апрув"-транзакция, а несколько инструкций в одной tx, видно в разделе "Дополнительно" Phantom. Подтверждает находку STK-32: клиент вручную поднимает лимит до 800 000 CU, т.к. дефолтных 200 000 не хватает.
- **Два отдельных попапа подтверждения для клейма** с чуть разными суммами MEX (0.07505 vs 0.075698) — по всей видимости, два клейма по двум разным позициям (не apply/approve-паттерн — на Solana программе не нужно разрешение пользователя, чтобы заплатить ему из своего же vault). Не подтверждено окончательно — предложено проверить полный список инструкций каждой транзакции или через Solscan, различить "две позиции" от "дубль одного и того же клейма". **Открытый вопрос, требует проверки.**
- **Разбор комиссии реальной `stake`-транзакции** (devnet, подпись `2VBmXnPr6deGx62267r6H99S2FEhy3r4U5FrejVmEA8Nfcupf6gYcSu3Lgryqt7MpFGxYrSywkMNWtrkqWHWcGns`):
  - Заявленная `Fee: 0.000305 SOL` = база (5 000 лампортов) + priority fee (цена CU 0.375 лампорта × **лимит** CU 800 000 = 300 000 лампортов) — совпадает с оценкой Phantom (~0.00031 SOL). Это ожидаемо и корректно.
  - Но фактическое списание с кошелька-плательщика составило `-0.00287284 SOL`, а рента за новый аккаунт `Position` (126 байт, 0.00176784 SOL, совпадает с формулой rent-exempt) + заявленная комиссия (0.000305 SOL) объясняют только `0.00207284 SOL`. Необъяснённый остаток — **≈0.0008 SOL (800 000 лампортов)**, не отнесённый ни к одному другому аккаунту транзакции. **Не подтверждено окончательно** — числа читались с округлённого UI (8 знаков), нужна точная проверка через `solana confirm -v <sig> --url devnet` или сырой RPC `getTransaction` (`meta.fee`, `preBalances`/`postBalances`), прежде чем считать это багом Explorer'а, реального перерасхода или ошибки фронтенда.
  - Отдельно (не связано с расхождением выше, но подтверждено точно): priority fee считается от запрошенного **лимита** CU (800 000), а не от факта (28 774 потрачено в этой транзакции) — то есть пользователь переплачивает почти в 28 раз против необходимого. Реальная численная демонстрация уже обсуждавшегося раньше риска (STK-32/`DEFAULT_COMPUTE_UNIT_LIMIT`).
- **Проверка ежедневного чек-ина**: подтверждено точным совпадением, что переход тира (Start 5% → Day 1 6%) корректно обновляет отображаемый APR и прогнозируемую месячную ставку (`+50.00/M` → `+60.00/M`, ровно `5%`/`6% × 1000 MEXICO`). Не удалось подтвердить по UI, что уже накопленная на момент чек-ина награда считается по **старой** ставке, а не пересчитывается задним числом по новой — из-за недостаточной точности отображения в USD (`<0.001`/`0.001`). Согласуется с уже подтверждённой на бэкенде гарантией (STK-04 — нет backdating начисления), но не является независимым математическим доказательством для фронтенда. Рекомендованный точный способ проверки: сравнить сырое поле `accrued` через RPC с расчётным (прошедшее время × старая ставка), а не доверять округлённому виджету.

### 5. Побочная тема — настройки Cursor (не относится к QA-находкам)

Пользователь спрашивал, как отключить постоянные запросы на подтверждение действий агента в Cursor. Ответ (через `cursor-guide`): **Settings → Agents → Approvals & Execution → Run Everything** (бывший "Yolo mode"); отдельно уточнено, что это не то же самое, что тумблер "Auto-Approve Mode Transitions" (он касается только переключения режимов Agent/Plan/Debug, не выполнения команд) — пользователь изначально перепутал эти два места. Также описаны Browser/File-Deletion/External-File Protection (могут спрашивать подтверждение даже при Run Everything), `permissions.json` для точечной настройки, и различия для CLI (`cli-config.json`/`--force`) и облачных агентов (там запросов на апрув нет вообще).
